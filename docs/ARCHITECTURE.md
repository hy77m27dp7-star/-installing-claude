# Architecture

One Cloudflare Worker, one D1 database, one R2 bucket, static assets served through the Worker, four cron triggers. TypeScript, strict, ESM, no Node-only APIs in `src/`. The character survives the model: her rules are code, her memory is rows, the model is a performer behind an adapter. v3 (SPEC_V3, "she will be human") adds nine modules on top and changes the turn pipeline's shape once; the sections at the end of this file cover them.

## Request flow

1. A request arrives at `src/index.ts`. Before anything else, `requireOwner` in `src/auth.ts` checks the identity. A failure is returned as a JSON 401, 403 or 503 and nothing else runs. This includes static pages, images and audio.
2. A state-changing request that a browser says came from another site (`Sec-Fetch-Site`, `Origin`) is refused with 403 before any handler. `/api/*` goes to the route table in `src/api.ts`. `/media/:id`, `/media/audio/:messageId`, `/media/inbox/:messageId/:n` and `/media/library/:id` go to the media servers (v3: `/media/:id` also serves a clip as `video/mp4` with Range support and a portrait as a png). Everything else goes to the ASSETS binding, which serves `public/` (the root serves `index.html`). Every response leaves with `private, no-store`, `nosniff`, HSTS, and for HTML a content security policy (v3: `connect-src 'self' https://api.openai.com` and `media-src 'self' blob:` so the call can run in the page, and a permissions policy granting the microphone to this origin only), no framing and no referrer.
3. A story turn is `POST /api/conversations/:id/turn` with `content` and an `idempotencyKey`, as JSON or as multipart with up to three image files. `runTurn` in `src/chat.ts` validates (content 1 to 4000 characters, key 8 to 80, images jpeg/png/webp up to 8 MB each) and loads the conversation. A voice message (`POST .../voice`) is transcribed first and then runs as the same turn with the transcript as its content.
4. Idempotency. If a user message with this key already has a reply, the stored pair comes back with `replayed: true` and no model call is made. If the message exists without a reply (the app died mid-turn), the turn continues with that message.
5. Context. `assembleContext` in `src/context.ts` loads the last 40 story messages (bounded to 24,000 characters; the last six of his messages carry their photos), the approved facts, the history entries that matter for the recent text, the open unknowns, the current relationship and scene versions, her life (threads and the last log rows), and the two callbacks picked for today, and builds the system prompt.
6. Budget. The prompt size gives an estimate; `assertBudget` compares today's and this month's spend plus the estimate against the two caps. Over a cap: 402, nothing written.
7. Generate. The provider named in settings is called with the system prompt, the messages, the model, max tokens and effort. On an opener turn (Let her start, or a first text) a one-time operator note is appended after the state sections and the final user turn is a fixed cue, so the cached prefix is untouched and no model reads the cue as his words. A thrown provider error or a refusal writes one failed run row and returns 502. No message is written and the scene does not move.
8. Markers. `stripMarkers` in `src/markers.ts` removes every `[photo: ...]` and `[song: ...]` from the text and keeps the last value of each; the voice tag `[voice]` and `[media: title]` come off the same way. A marker may sit anywhere; a line that held only a marker disappears.
9. Checks. `runChecks` returns flags and an action. Retry means one more call with a corrective note; repair means a mechanical cleanup. Two v2 flags are added here, never changing the action: `song_marker_dup` and `callback_forced`. See docs/BEHAVIOR.md.
10. Delivery time. In real mode (`replyDelayMode: "real"`), `computeDeliverAt` in `src/life.ts` sets `deliver_at` on her message from her life: a busy block delays until it ends, capped at `realDelayMaxMinutes`, with 20 percent jitter; a free moment is 5 to 90 seconds. The jitter is seeded by the message id so a retried commit lands on the same instant. Instant mode and opener turns leave it null.
11. Commit. One `db.batch`: the user message (none on an opener turn), the run row (and the retry's run row), the assistant message with its flags, `song_json` and `deliver_at`, the `message_context` row (section below), the conversation timestamp, the usage row, and, when a photo was asked for, the photo request (a `visual_assets` row with status `pending` and the description as its prompt) with the message pointing at it (`image_id`, `image_status: "pending"`). Either everything lands or nothing does.
12. Respond with the `TurnResponse`: both messages (`userMessage` null on an opener), `deliverAt`, the run summary with cost, the flags, `imagePending`.
13. After the response, in `ctx.waitUntil`: the proposal pass runs if proposals are on, and her voice note is made when the message ends with `[voice]` or voice mode is `all`. Best effort; a failure is logged as a run and swallowed. The turn is already committed. The photo is not made here: Workers cancel `waitUntil` work 30 seconds after the response is sent and an image call takes longer, so the Chat page asks for it with its own request (next section).

The operator channel (`POST /api/operator`) is a separate path in `src/operator.ts`. It answers with deterministic facts from `systemInfo` and, on a real provider, one model call under the operator prompt. Its messages are stored with channel `operator` and are never read by story context assembly.

`GET /api/conversations/:id/messages` hides her replies whose `deliver_at` is still in the future; the Chat page asks with `?includePending=1`, shows typing dots until the time, and then the bubbles. A reload keeps the message hidden the same way. The delay is never explained in the story.

## Prompt layout

`src/prompt.ts` builds the system prompt in two parts.

The stable prefix comes first: the always-on rules, the runtime overlay, and the reference files (core identity, relationship and evolution, text and style, conflict and boundaries, tastes and visual canon, knowledge boundary). It is assembled from `src/generated/constitution.ts`, which `scripts/build_constitution.mjs` produces from the frozen files in `canon/constitution` plus the adaptation list (22 replaces 24, the music list is removed, and so on). v2 adds two things to the overlay through that script: the SONGS rule (one `[song: Artist - Title]` line at most, her taste not his, never named twice) and the photo-look line (when he sends a photo she reacts to what is in it, never an inventory). The prefix is identical bytes every turn. The Anthropic adapter sends it as one system block with a cache breakpoint, so repeat turns read it from the cache.

The state sections follow, from D1, approved rows only: fixed canon; things true about her, split into told and untold, with opinions kept under their `opinion:` prefix so she knows what she has already said she thinks; what she knows about him (only what he said); shared history; MODE (together: "You are in the same place as him right now: {location}"; apart: "You are texting from {where her life has her, or wherever your day has you}"); the current relationship and scene JSON with her mood and, while a cooling-off is still running, the cooling-off lines (shorter replies, less warmth, no punishment, no threats, no silence as a weapon; repair needs his honest, specific acknowledgment); open unknowns; YOUR LIFE RIGHT NOW (section below); THINGS YOU COULD BRING UP (section below); THINGS ON YOUR PHONE YOU COULD SEND (the library titles); and, while shared history is empty, the first-conversation file. The prompt version is the constitution version plus a prompt revision suffix (p4 for v2), and it is stored on every run.

Nothing the model said last turn is in the prompt except as ordinary conversation messages. Developer notes, flags and operator messages never enter it. An opener note is appended once, after the state sections, and only on that turn.

## Her life

`src/life.ts`. Two tables from migration 0004: `life_threads` and `life_log`. A thread has a kind (routine, event, person, place, arc), a title, a detail line, an optional schedule, a relation (people), a source, and the same versioning as facts: an edit inserts a new row with `supersedes_id` and marks the old one superseded; drop is a new head with status dropped; restore brings any version back as the newest active row. Every write is audited in the same batch. The log is flat: a time, a note, an optional thread.

Schedules are JSON. A routine holds blocks by weekday with start and end times (`{ "blocks": [{ "days": [1,2,3,4,5], "start": "09:00", "end": "17:30", "label": "at work" }] }`); an event holds one instant with a length (`{ "at": "2026-10-03T19:30:00-04:00", "minutes": 120, "label": "open mic" }`). The pure half of the module (`whereSheIs`, `lifeSection`, `computeDeliverAt`) never touches the database and does its timezone work with `Intl.DateTimeFormat` alone, in her timezone from settings (America/New_York by default), so the unit suite runs it under Node on fixed clocks.

`whereSheIs` resolves the active routines and events against now and answers busy or free, with a label and an end time; overlapping blocks keep her busy until the last one ends. `lifeSection` renders YOUR LIFE RIGHT NOW: the local day and time, the current block if any ("You are at work until 5:30pm"), the next event within seven days, her week, the people (name, relation, one line), the places (with the last note there), the arcs ("where things stand"), and the last five log notes. When nothing is recorded it says so and tells her she still has days and may mention ordinary things when they fit; they become real once the owner records them. Nothing is seeded on purpose.

Her life fills two ways: the Life tab, or a `life` proposal from the proposal pass (a statement by her about her own days: a job, a class, a regular plan, a person, a place; never from a joke) that he approves, which creates the thread.

## Callbacks

`src/callbacks.ts`, pure. Candidates: approved history entries older than three days, active arcs, people, events from the past 14 days, and log notes from the past 14 days. Anything whose identifying words (a name, a title) or three words of its line appear in the last 20 messages is dropped. The rest is ordered by a seed (the UTC date plus the conversation id), so the same two stay on offer through a day, and two are picked, from different kinds when possible. They render as THINGS YOU COULD BRING UP with the elapsed time ("11 days ago: ...") and a line that says one at most, or neither, the way it would come up in a text. It is never an instruction to ask a question. When both land in one reply the `callback_forced` flag records it.

## Provenance

`src/provenance.ts`. Every reply gets one `message_context` row, written in the turn's own batch: prompt version, provider, model, the history ids, the fact ids (hers and his), the thread ids, the callbacks offered, the unknown ids, how many recent messages were in the window, the flags, the mode, the run ids, whether a retry happened, the delivery time, the song, whether a photo was requested, and whether it was an opener. Ids and counts only, never prompt text, never a secret; the row is capped at 64 KB. `GET /api/messages/:id/context` returns it and the Chat page's why panel resolves the ids to titles. His messages, operator messages and v1 rows have no row (404).

## Memory model

Every durable thing is a row, every change is a new row, every write is audited.

- Facts (`facts`): scope fixed, avelie, justin or shared. Fixed rows are read-only through the API (403 fixed_canon). Avelie facts carry `disclosed` (has she said it out loud) and `provisional`. An edit inserts a new version with `supersedes_id` and marks the old row superseded; delete is a supersede with status rejected; restore inserts a copy of an old version as the newest. Opinions are avelie facts whose subject starts with `opinion:`; an approved `opinion_change` proposal supersedes the row with the same subject (case-insensitive) instead of adding a second one, so the chain shows her mind changing.
- History (`history`): the shared timeline, ordered by `seq`, with title, when, body, what changed, what to keep consistent. Same versioning as facts. It is empty now; when it stops being empty, the first-conversation section leaves the prompt and the first_meeting_replay check turns on.
- Unknowns (`unknowns`): real gaps she must not resolve by guessing. Open or resolved, with a resolution note.
- State versions (`state_versions`): relationship and scene are append-only JSON versions. Save appends; restore appends a copy of the chosen version. The prompt always reads the newest. The relationship state may carry `mood` and `cooling_off_until` (validated; no automatic decay; he clears it or an approved `relationship` proposal with `cooling_off_hours: 0` ends it). The scene status is together, apart or none.
- Her life (`life_threads`, `life_log`): above.
- Proposals (`proposals`): what the proposal pass thinks was durable in one exchange, with the kind, the quote it rests on, a confidence and, in v2, a structured payload (a life thread; a mood and cooling-off hours; an opinion subject). Pending until you approve, edit or reject in the inbox. Approval promotes through the state helpers above, so a promoted row is versioned and audited like a hand-written one. Duplicates of pending proposals and approved facts are dropped on the way in.
- Message context (`message_context`): above.
- Messages (`messages`): v2 adds `deliver_at`, `song_json`, `audio_key` (her voice note or his recording), `images_json` (the photos he sent: keys and sizes) and `media_id` (a library item she sent).
- Audit (`audit_events`): actor, action, entity, before and after JSON, for every write that changes canon, state, images, settings, her life, the library, push subscriptions, and every cron run.
- Runs (`model_runs`): every model call, including failed, refused, drift and voice ones, with provider, model, prompt version, tokens, cost, latency, status and flags. The error field holds a class, never a message that could echo a key.
- Drift reports (`drift_reports`), first-text counts (`first_texts_daily`, one row per day), push subscriptions (`push_subscriptions`, one per endpoint), the media library (`media_library`), voiceprints (`voiceprints`, one per week).
- Snapshots (`snapshots`): the full export taken automatically before an import replaces anything.

## Image pipeline

She asks for a photo by putting one marker in a reply: `[photo: what it shows, outfit, place, expression, selfie or taken by someone]`. The marker is removed before the message is stored or shown; only the description survives.

1. The turn commits the request: a `visual_assets` row with status `pending` holding the description, and the message with `image_status: "pending"` and `image_id` naming that row. The Chat page shows a placeholder and sends `POST /api/images/generate { conversationId, messageId }`, and keeps that request open until the picture exists. A request the page holds open has no time limit; background work in a Worker is cancelled 30 seconds after the response, which is why the photo is never made in the background. A reload resumes any message still pending. If another request already holds the picture (a second tab, an earlier attempt), the server answers 409 `in_progress` and the page polls the message every 3 seconds for up to 2 minutes instead.
2. `generateCandidate` in `src/images.ts` claims the request (status `generating`, with a timestamp; a claim older than four minutes counts as abandoned and is taken over), then checks that the image provider is configured, checks the budget with the flat photo price, and loads the masters through the ASSETS binding: the three strongest, in `MASTER_ORDER`, the tight face crop first (`MAX_REFERENCES` is 3 since 2026-09-25; fewer, stronger references hold a face better than all of them at once). Each master's bytes are hashed and compared to the registry; a master that has drifted stops the run, because a wrong reference is worse than no photo.
3. The prompt is the fixed identity block from `imageIdentityPrompt()` (her face, hair, skin, build, age 22, candid phone-photo style, no text, no collage) followed by ` Scene: ` and her description. Only outfit, setting, pose, expression and lighting vary.
4. The adapter named by `imageProvider` makes the picture. Runway (`runway`, the photo provider since 2026-09-25, section "Photos on Runway" below): Gen-4 Image with the references tagged `@avelie`, `@avelie_2`, `@avelie_3`, a short identity line of its own in place of the block from step 3, a task polled inside the same request, the output downloaded. OpenAI (`openai`, the fallback): a multipart request to `images/edits` with the model, the prompt, size, quality, `n=1`, `input_fidelity=high`, and the references as `image[]` PNG blobs, with a 180 second timeout; it reads `data[0].b64_json` and decodes it. For both, 401 is an auth error, 429 is a rate limit, 400 (including a content policy refusal) is a non-retryable bad request, 5xx is a server error; a Runway moderation failure is a non-retryable refusal. Locally the stub adapter returns master 03's bytes so the whole path runs without a key.
5. The result is hashed. If the hash matches any rejected asset, the candidate is refused (422 blacklisted) and never stored.
6. The PNG goes to R2 as `candidates/<id>.png`. One batch then turns the request row into the candidate (status candidate, hash, size, provider, model), writes the run row with the photo cost, the usage row, an audit event, and sets the message's `image_status: "ready"`.
7. On any failure the run row is written as failed, the request row becomes `failed` with the reason in its notes, and the message's `image_status` becomes `failed`; the Chat page shows the error code and a Retry control that re-requests the same description. Her text reply is already stored and stays.
8. `GET /media/:id` streams the PNG from R2, only for a candidate or an approved scene image, with `cache-control: private, no-store`. Anything else is 404.
9. Approve sets status approved and role scene; the message keeps its picture. Reject deletes the R2 object, keeps the row with its hash so the blacklist persists, and sets the message's `image_status` to `rejected` so the Chat page hides it. Regenerate (v2) rejects and then runs the same description again for the same message; the rejected hash stays blacklisted.

You can also ask for a photo yourself with `POST /api/images/generate` and a description; it is the same pipeline. `POST /api/assets/verify` hashes the five masters from ASSETS and compares them with the registry; the Images page has the button. The Photos drawer on the Chat page lists the approved scene images newest first and scrolls to the message a picture belongs to.

## Vision: photos he sends

A multipart turn may carry up to three images. Each is stored in R2 as `inbox/<messageId>/<n>.<ext>` and `messages.images_json` holds the keys and sizes; `GET /media/inbox/:messageId/:n` serves them back to the Chat page. `assembleContext` attaches images only for the last six of his messages, to bound cost. The adapters send them the way each API wants (Anthropic: base64 image blocks before the text; OpenAI: `image_url` data URLs; Workers AI: a vision model when the configured model is one, otherwise the images are dropped and a plain line says he sent a photo she could not open, so she never pretends). The stub answers "(photo received)". The overlay line tells her to react to what is in the picture with her taste and her mood, never to describe it back like an inventory.

## Voice

Out (`src/voice.ts`): when her message ends with `[voice]` (voice mode `some`) or on every reply (`all`), `synthesize` makes an mp3 after the response, in `ctx.waitUntil`: Workers AI's text-to-speech model by default (no key), ElevenLabs with `ELEVENLABS_API_KEY` and a voice id, or off. The audio goes to R2 as `voice/<messageId>.mp3`, `messages.audio_key` points at it, and `GET /media/audio/:messageId` streams it after the owner gate. A failure leaves the text message as it is and writes a failed run. The tag comes off the text like any marker; the overlay allows it "when you would rather say it than type it, rarely".

In: the composer's hold-to-record button captures webm/opus with MediaRecorder and posts it to `POST /api/conversations/:id/voice` (60 seconds, 4 MB). The Worker stores it as `voice_in/<id>.webm`, transcribes it (Workers AI whisper by default, OpenAI with its key), and runs the normal turn with the transcript as the content; his message carries `audio_key` too and the Chat page shows the transcript with a mic chip.

## Media library

`src/media.ts`. The owner uploads a clip, video or image (25 MB) with a title and a description through `POST /api/media`; it lives in R2 as `library/<id>.<ext>` with a `media_library` row (kind, title, description, key, mime, bytes, sha256, status). The prompt lists the titles and one-line descriptions under THINGS ON YOUR PHONE YOU COULD SEND, and the overlay says: only when it fits, never on a schedule, never to fill silence. She sends one with `[media: <title>]`; the runtime matches the title case-insensitively, sets `messages.media_id`, and the Chat page renders an audio, video or image card. An unknown title strips the marker and adds `media_unknown`.

## Cron

`src/index.ts` exports `scheduled(event, env, ctx)` next to `fetch`. `event.cron` picks the job; each job runs on its own, writes an audit event, and never throws past the handler (a failure is logged by class). The four triggers in wrangler.jsonc:

- `0 7 * * *` (daily 07:00 UTC): `runBackup` in `src/backup.ts`. `exportAll` to R2 `backups/avelie-<YYYY-MM-DD>.json`, then the list under `backups/` is trimmed to the newest 30. The same JSON State > Import takes back.
- `0 13 * * 1` (Monday 13:00 UTC): `runDrift` in `src/drift.ts`, only when `driftCheckEnabled` and a real text provider is configured. Five scenarios tagged `drift: true` (bundled into `src/generated/` at build time from `tests/behavior/scenarios.json`, or embedded, whichever the drift lane chose; its report says), one throwaway conversation with status `drift` that the chat list never shows, the same `runTurn` and checks as any turn, spend through the caps, one `drift_reports` row with the transcripts and flag counts, then the throwaway messages deleted. `POST /api/drift/run` is the same by hand.
- `*/20 * * * *`: `maybeTextFirst` in `src/herfirst.ts`. The decision is a pure function over the settings, the count for today, the time in her timezone, `whereSheIs`, the last message's age and author, and a deterministic per-tick probability (remaining today over remaining ticks in the waking window). On a send it calls `runTurn` with the first-text opener note on the most recent active conversation (a new one titled by the date if none), counts it in `first_texts_daily`, and sends the push. A `dependency_hook` flag on the draft drops it, logs it, and ends the tick.
- `0 14 * * 1` (Monday 14:00 UTC): `runVoiceprint` in `src/voiceprint.ts` over her story-channel messages of the week: count, mean and median length, share ending with "?", share with "lol" or emoji (should be zero), share containing his name, top 25 words minus stopwords, bubble count per reply, first-text count, flags per code. One `voiceprints` row per week; the Model page shows the last eight with two small inline sparklines.

Locally, `wrangler dev --test-scheduled` exposes `/__scheduled?cron=<cron string>` so the integration runner and a person can call any handler by its cron string.

## Push and the phone shell

`public/manifest.webmanifest` and `public/sw.js` make the app installable. The service worker registers only after a page has loaded behind the login, caches the shell (pages, css, js, the icon), never caches `/api` or `/media`, and on a `push` event fetches `GET /api/push/latest` (which carries the Access cookie like any request) and shows her latest first text as a notification; a tap focuses or opens `/`.

`src/push.ts` sends Web Push with no payload at all: an empty body signed with a VAPID ES256 JWT built with `crypto.subtle` from `VAPID_PRIVATE_KEY` (audience is the push endpoint's origin, expiry at most 24 hours). No message text ever travels through a push service; the service worker fetches it from the Worker. Subscriptions are `push_subscriptions` rows (one per endpoint) written by `POST /api/push/subscribe` from the Model page's Notifications switch. Push is sent only for her first texts. Without the two VAPID secrets `GET /api/push/public-key` answers 503, the switch stays off, and a first text is logged as "push skipped".

## Timeline

`src/timeline.ts` merges history entries, approved photos, media she sent, life log notes, relationship and scene versions and her first texts into one list ordered by time, 500 at a time with `?before=` for paging, each item with a date, a type, a title and a link to the message or the state version. `public/timeline.html` renders it read-only, newest at the bottom. Nothing on that page writes.

## Character export

`src/exportCharacter.ts`. `GET /api/export/character` returns one JSON package: the constitution version and its adaptations, the fixed canon, her facts and opinions, the history, her life, the unknowns, the relationship and scene, the approved images with hashes, the library titles, and a SHA256 of the stable prompt prefix (so two deployments can prove they run the same rules without shipping the text). `GET /api/export/character.md` renders the same as a readable bible with a heading per section. No key, no prompt text, no message transcript. The v1 `GET /api/export` remains the full backup and now carries the v2 tables.

## Auth

Every request, including static assets and `/media`, passes `requireOwner` first. There are exactly two ways in. (The `/__scheduled` path exists only under `wrangler dev --test-scheduled`; production has no such path.)

Production: the request carries the Access JWT in the `CF-Access-Jwt-Assertion` header or the `CF_Authorization` cookie. The Worker fetches the team's JWKS from `https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs` (cached in memory; refetched when a token names an unknown key id, at most once a minute, and in any case once a day), verifies the RS256 signature with `crypto.subtle`, and checks the issuer is `https://<ACCESS_TEAM_DOMAIN>`, the audience contains `ACCESS_AUD`, the token has not expired, and the email equals `OWNER_EMAIL` case-insensitively. Anything else is 403. If the JWKS cannot be fetched and nothing is cached, 503.

Local: only when `APP_ENV` is not `production`, `ACCESS_AUD` is empty, the request host is `localhost` or `127.0.0.1`, and `DEV_ACTOR_EMAIL` is set in `.dev.vars`. Then the actor is that email. Production never has `DEV_ACTOR_EMAIL`, and with `APP_ENV=production` the local rule is off whatever else is set. A refused token answers a fixed 403 body with no reason; the verifier's reason (wrong audience, wrong email, bad signature, expired, unknown key id, wrong issuer, malformed) goes to the log as a class-level message, never with the token.

With `ACCESS_AUD` empty and no local actor, every request is 503 "access not configured". The Worker fails closed. No header from the browser is ever trusted as an identity, and nothing in `src/auth.ts` logs a header, a token or a key. Cron jobs run inside the Worker with no request and no identity; they act as the system and are audited as such.

## Provider adapter

Settings name a text provider (anthropic, openai, workersai, stub), an image provider (runway, openai, stub), a voice provider (workersai, elevenlabs, off, stub) and a transcribe provider (workersai, openai). `src/providers/index.ts` hands back the adapter and says whether the environment holds what it needs: the stub and Workers AI need nothing; Anthropic needs `ANTHROPIC_API_KEY` (and, for an org-level key, `ANTHROPIC_WORKSPACE_ID`); OpenAI needs `OPENAI_API_KEY`; ElevenLabs needs `ELEVENLABS_API_KEY`; Runway needs `RUNWAY_API_KEY`, for clips and for photos alike, checked at call time so the Model page can be switched to it before the secret exists (the photo then fails as 503 `provider_not_configured` until it does). Every adapter maps its own errors into one `ProviderError` with a kind (auth, rate_limit, bad_request, server, network, config) and a retryable flag, so the turn pipeline never sees a raw SDK error and never logs one.

Anthropic (`src/providers/anthropic.ts`): the official SDK, retries off (the pipeline's own retry is the only one, so a timed-out call is never billed twice). The system prompt goes as one text block with `cache_control: { type: "ephemeral" }`, the messages follow (image blocks before the text on a message that carries photos), `max_tokens` is the settings value, and `output_config.effort` is the settings effort. Thinking is left at the model default. Input tokens are counted as `input_tokens` plus `cache_read_input_tokens` plus `cache_creation_input_tokens`, so the meter sees every token the model read. Stop reason `refusal` becomes a refused run, `max_tokens` is passed through (and flagged `truncated`), anything else is a normal end.

Temperature is never sent to Anthropic, and neither is top_p or top_k. The exact reason: Claude Opus 5, Claude Sonnet 5, Opus 4.7, Opus 4.8 and the Fable models reject sampling parameters with an HTTP 400 invalid_request_error. A request carrying `temperature` would fail on every turn, which the pipeline would record as a failed run with no reply. On these models `output_config.effort` is the only depth control, and that is what the Model panel's effort setting maps to. The temperature field in the Model panel still applies to the OpenAI and Workers AI adapters, which accept it.

OpenAI text (`src/providers/openai.ts`): `POST /v1/chat/completions` over fetch with a system message, the messages (photos as `image_url` data URLs), `temperature` and `max_completion_tokens`. `finish_reason: "content_filter"` or a refusal field is a refusal; `"length"` is max_tokens. The images adapter lives in the same file and is described above.

Workers AI (`src/providers/workersai.ts`): `env.AI.run(model, { messages, max_tokens, temperature })`. Accepts a string or `{ response }` result. Token counts are zero when the runtime does not report them, so the meter cannot price it; a model without a price entry is refused by the caps rather than metered at zero. It is for comparison, not for the daily meter.

## v3: the turn in three pieces

`runTurn` in `src/chat.ts` is now built from three exported pieces so a tasting can reuse them without a second pipeline: `prepareTurn` (validation, idempotency, the pending-tasting gate, the provider check, the context with `systemParts`, the budget estimate, the request, the check context, the callbacks), `generateDraft` (the call, the checks, the one retry, the run rows priced by the performer named), and `commitReply` (the one batch: the user row when new, the run rows, the assistant row, the photo request, the provenance with the state text, the memory touches, the exemplar uses, the recall row, the conversation touch). The system prompt is sent as two parts. `GenerateRequest` carries `systemParts: { prefix, state }` next to the joined `system`; the Anthropic adapter (`systemBlocks`) sends the prefix as one block with the cache breakpoint and the state as a second block without one, so a per-turn change in the state never misses the whole prompt. ## v3: human memory

## Photos on Runway (the character-reference image provider, 2026-09-25)

Why: four OpenAI pictures were rejected on 2026-09-25 because the face drifted and the body never came from the references. Runway's Gen-4 Image takes tagged character references and is asked for the same person by name, so it is the photo provider now; OpenAI stays selectable as the fallback (`imageProvider: "openai"`). Nothing else in the pipeline moves: `generateCandidate` still claims, budgets, loads the same references, hashes, blacklists and stores exactly as before; only step 4 changes hands.

`runwayImageProvider` in `src/providers/runway.ts` (the video adapter's file; the two share the key, the headers, the task read and the download):

1. References: the bytes `loadMasterBytes` returns (face crop first, at most three), each sent as a base64 data URI (`data:image/png;base64,...`, the mime sniffed from the bytes) with a distinct tag: `avelie`, `avelie_2`, `avelie_3`. A reference whose data URI would pass 5 MB is refused before encoding (413, non-retryable). The masters sit behind Access, so no URL of ours would work as a reference.
2. Prompt: `runwayImagePrompt(scene, tags)`: "@avelie is the woman in every reference image (@avelie_2 and @avelie_3 are the same person as @avelie). Show exactly her: her face as @avelie_3 and the other references show it, feature for feature, as beautiful as in the references, fully visible, lit softly and flatteringly even at night; a clearly adult 22-year-old, fully clothed. Dresses well: fitted, flattering clothes, upright posture, never frumpy or slouched. Setting, clothes and pose from the scene. Polished, flattering photo, no text, no watermark, one image. Scene: " + her description, cut at a word, + " Her figure here as @avelie and @avelie_2 show it: a small slim frame, slim waist, flat stomach, with a full bust and a full shapely backside, an hourglass under any outfit, never heavy." References ride body-first (05 the black dress, 04 the blazer, 00 the face crop). Runway caps the prompt at 1000 UTF-16 units, so the boilerplate stays under 720 and the scene gets the rest; the body clause comes AFTER the scene because the model follows the scene over an earlier line. "Candid ... natural imperfections" was dropped on 2026-09-25 because every picture came out rougher than the masters; words that risk moderation stay out (the unit test scans for them).
3. Ratio: `ratioForSize(imageSize)` picks the enum value nearest the requested WxH (exact match, then closest aspect, then closest pixel count among aspects within 2 percent): `1024x1536` becomes `1080:1440`, `1024x1024` stays, `auto` is `1080:1440`. `imageQuality` has no equivalent on Gen-4 Image and is not sent.
4. Task: `POST /v1/text_to_image`, then `GET /v1/tasks/{id}` every 3 seconds inside a 90 second budget, inside the one request the Chat page holds open (the 4 minute claim lease covers it). Past the budget the task is cancelled (`DELETE /v1/tasks/{id}`) so an unwatched picture is not paid for, and the failure is a retryable server error.
5. Output: the first `output` URL is downloaded (https only, no key on that request, 20 MB cap) and handed back as the bytes `generateCandidate` hashes and stores. The URL itself expires within 24 to 48 hours and is never stored.
6. Failures: HTTP 401/403 auth, 429 rate_limit (retryable), 400/404/413/415/422 bad_request, 5xx server (retryable), transport network (retryable). A task that comes back `FAILED` with a `SAFETY.*` or `INPUT_PREPROCESSING.SAFETY.*` code is a non-retryable `refusal` (the request row's notes say `refusal: moderated by Runway (SAFETY.INPUT.TEXT: ...)`); `ASSET.*` is a bad request; `INTERNAL.BAD_OUTPUT.*`, `INPUT_PREPROCESSING.INTERNAL`, `THIRD_PARTY.UNAVAILABLE` and a missing code are retryable server errors; `CANCELLED` is not retried. Every message passes through `redactSecrets` before it is stored or logged.
7. Portraits (`generateFromText`, SPEC_V3 DD) run on it too: the same task path with no references and the portrait size's ratio (`gen4_image` accepts zero references; `gen4_image_turbo` requires one to three and would answer 400).
